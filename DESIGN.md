## Problem Statement

Les pilotes drone certifiés UAS (indépendants, fonctionnaires, salariés de bureaux d'études)
passent entre 30 minutes et 2 heures à produire chaque rapport d'inspection post-mission —
formatage manuel Word/PowerPoint, intégration des orthophotos, classification des anomalies,
mise en page pour livraison client. Il n'existe pas de solution simple, abordable et en français
pour ce cas d'usage spécifique. Les outils existants (DroneDeploy, Pix4D, Sterblue) sont
des plateformes enterprise complexes ciblant les grands opérateurs industriels.

## Demand Evidence

- Le créateur est lui-même pilote drone (fonctionnaire réalisant des missions pour des
  collectivités) et vit la douleur directement
- Durée de production d'un rapport : 30min à 2h, couvrant l'ensemble du pipeline
  (structuration, intégration photos, classification, livraison)
- Workflow actuel : aucun standard — chaque pilote fait à sa sauce, pas de format unifié
- Le marché existant est fragmenté vers l'enterprise : pas d'outil SMB/indépendant en
  français confirmé

**Note :** Les attentes précises des clients commanditaires n'ont pas encore été validées
(voir prémisse 4 et open questions).

## Status Quo

Aucun standard dans le marché SMB/indépendant :
- Word avec copier-coller manuel
- Chaque pilote livre ce qu'il a, pas de format cohérent
- Pas d'outil dédié au reporting seul (les plateformes existantes font tout sauf être
  accessibles à un indépendant à 9€/rapport)

Coût réel du statu quo : 30min-2h de travail improductif par mission, répété à chaque livraison.

## Target User & Narrowest Wedge

**Cible initiale :** Pilote drone auto-entrepreneur certifié UAS, réalisant des missions
d'inspection répétitives (toiture, façade, infrastructure municipale...), livrant des rapports
à des clients artisans/PME/collectivités.

**Persona :** Auto-entrepreneur, 5-15 missions d'inspection par mois, chaque heure de
reporting non-facturée réduit directement son revenu. Paie par rapport tant que l'outil
lui fait gagner >1h de travail.

**Expansion prévue (post-validation) :**
- Fonctionnaires / agents territoriaux réalisant des missions pour des collectivités
- Salariés de bureaux d'études / BTP

**Wedge le plus étroit :** Un rapport d'inspection de toiture complet (infos chantier →
zones → anomalies avec sévérité → photos annotées → PDF) généré en moins de 10 minutes,
téléchargeable immédiatement après paiement 9€.

## Constraints

- Le modèle pay-per-report (9€) doit être viable avec des coûts variables bas
- PWA (pas d'app store, accès immédiat depuis terrain)
- Langue française obligatoire pour le marché cible
- Attentes clients commanditaires non encore validées : le format PDF doit être
  professionnel mais peut ne pas correspondre à une norme formelle inconnue
- Les coûts IA doivent rester < 1€/rapport pour maintenir la marge

## Premises

1. Le problème principal est "assembler un rapport professionnel vite", pas "analyser
   les données drone" (valide pour V1 ; l'analyse IA est la roadmap V2+)
2. Les pilotes indépendants paieront 9€/rapport si ça leur fait gagner 1h+ de travail
3. Il n'existe pas de solution simple et abordable en français pour ce cas d'usage
4. [RISQUE VALIDÉ] Les attentes des clients commanditaires sur le format ne sont pas
   encore connues — à valider avant de figer la structure du PDF

## Approaches Considered

### Approach A: Le formulaire structuré (MVP pur)
- PWA multi-étapes : infos mission → zones inspectées → anomalies (drag-and-drop sévérité)
  → upload photos annotées → génération PDF → paiement Stripe 9€
- Zéro IA, zéro coût variable hors infrastructure
- Effort : S (2-3 semaines) / Risque : Faible
- Valide l'hypothèse de paiement avant tout investissement supplémentaire

### Approach B: L'assistant IA dès le départ
- Upload photos → IA Vision détecte anomalies → pilote valide → rapport
- Effort : L (2-3 mois) / Risque : Élevé
- Coût variable 0.50-2€/rapport comprime la marge sur 9€
- Différenciant fort mais risque de construire avant validation du paiement

### Approach A+B: Formulaire structuré + IA légère (CHOIX RETENU)
- Socle : formulaire structuré multi-étapes (Approche A)
- Touche IA : suggestions de sévérité et de libellés d'anomalies via LLM sur description
  textuelle (pas vision — beaucoup moins cher, ~0.02€/requête)
- Effort : M (3-4 semaines) / Risque : Faible-Moyen
- Permet de différencier sans exploser les coûts

## Recommended Approach

**Approche A+B : Formulaire structuré + IA légère (suggestions textuelles)**

Stack suggéré :
- Frontend : React PWA (Vite + TailwindCSS)
- Génération PDF : react-pdf (côté client, zéro coût serveur, génération instantanée)
  — pas Puppeteer en V1 (latence, mémoire, incompatible Vercel Serverless)
- IA légère : Claude Haiku via API Anthropic (suggestion de sévérité/libellés, < 0.02€/appel)
- Paiement : Stripe Checkout (pay-per-report) + Stripe Billing (abonnements)
- Backend : Supabase (auth magic-link + stockage photos temporaire + Edge Functions)
- Hosting : Vercel (frontend) + Supabase (backend)

**Modèle d'identité :**
- Pay-per-report : l'utilisateur fournit son email → lien de téléchargement envoyé par email
  (pas de mot de passe, session valable 24h dans le navigateur)
- Abonnements : magic-link email → compte persistant avec historique des rapports
- Upgrade naturel : un acheteur pay-per-report peut créer un compte après son premier rapport

**Stockage photos :**
- Upload vers Supabase Storage (bucket privé, URL signée temporaire)
- Rétention : 48h après génération du PDF, puis suppression automatique
- Formats acceptés : JPEG, PNG, WEBP — max 10 photos par rapport, max 5MB/photo
- Embedding PDF : photos redimensionnées côté client avant injection dans react-pdf

**Flow utilisateur (6 steps — TASTE-1 résolu : pattern zone-card) :**
1. Accueil → "Créer mon rapport" → email requis + prompt "Continuer votre rapport" si draft localStorage détecté
2. Infos mission (client, adresse, date, type d'inspection [dropdown], météo [Ensoleillé/Nuageux/Pluvieux/Vent fort], drone utilisé)
3. Zones + anomalies inline (zone-card) : liste de zones pré-peuplée selon type d'inspection
   (ex. toiture → Pan Nord, Pan Sud, Rive Est, Rive Ouest — éditable). Chaque zone-card se
   déplie pour saisir ses anomalies. Sévérité : Faible / Modéré / Grave / Critique.
   Bouton "Obtenir une suggestion IA" par anomalie → appel Claude Haiku non-bloquant
   (timeout 3s — si échec, disparaît silencieusement, pas d'erreur affichée).
   État chargement bouton : "Analyse en cours..." + spinner.
4. Upload photos : `<input type="file" accept="image/*" capture="environment">` (caméra directe
   sur mobile). Per-photo state: pending / uploading (X%) / done / failed. Retry individuel.
   Résolution max embeddue : 1200px large, 200KB par photo (downscale immédiat sur `<input>` change).
   "Générer l'aperçu" désactivé tant que toutes les photos ne sont pas `done`.
   Zone + anomalie associée via menus déroulants (pas de dessin en V1).
5. Prévisualisation PDF : bouton "Générer l'aperçu" (react-pdf on-demand, client-only).
   Chaque section de l'aperçu a un lien "Modifier" → retour au step correspondant.
   Police : Noto Sans (Latin-1 complet — caractères français accentués garantis).
   Progress indicator par page rendue. Si crash : "Erreur lors de la génération — vos données sont sauvegardées. Réessayer."
   [TASTE-2 : Fallback serveur reporté en V1.1 — mitigation par downscale 200KB]
6. Paiement 9,00 € Stripe → /verify-payment (vérification synchrone Stripe API) → lien
   téléchargement envoyé par email + téléchargement immédiat. Token de téléchargement = UUID v4
   (non-devinable). Si paiement refusé : "Paiement refusé — vérifiez votre carte ou réessayez.
   Vos données sont sauvegardées." Si webhook manquant : /verify-payment est le chemin primaire,
   webhook = confirmation secondaire idempotente.

**Modèle de prix V1 (scope réduit) :**
- Pay-per-report : 9€/rapport (Stripe Checkout)
- Starter : 29€/mois — 5 rapports
- Pro : 59€/mois — rapports illimités + templates personnalisés

**Hors scope V1 (tiers Équipe reporté) :**
- Équipe multi-utilisateurs (99€/mois) : nécessite système de permissions/organisations —
  à construire uniquement après validation par des paying customers Pro

## Open Questions

1. **Format client commanditaire (BLOQUANT pour V1.5)** : quelles informations les
   donneurs d'ordre exigent-ils ? Existe-t-il des normes AFNOR, CCTP types, ou références
   réglementaires applicables ? À valider par 3-5 entretiens avec des commanditaires
   avant de figer la structure PDF définitive.
2. **Régime d'achat collectivités** : les fonctionnaires/agents peuvent-ils acheter
   via pay-per-report (carte perso) ou faut-il un devis/bon de commande ? Si collectivités
   = segment visé ultérieurement, prévoir une option "facturation structure".
3. **Types d'inspections prioritaires** : toiture d'abord ? Façade ? Infrastructure
   municipale ? Prioriser 1-2 types pour les templates V1.
4. **Conformité RGPD** : les photos d'inspection peuvent contenir des données sensibles
   (adresses, propriétaires) — politique de rétention des données à définir.

## Success Criteria

- 10 pilotes paient au moins 1 rapport en < 4 semaines après lancement
- Temps de production d'un rapport < 10 minutes (vs 30min-2h actuel)
- Taux de conversion "prévisualisation → paiement" > 40%
- NPS pilotes > 7/10

## Distribution Plan

- Lancement : Product Hunt France + groupes Facebook/LinkedIn "Pilotes drone France"
- Canaux : forums spécialisés (dji-forum.fr, communautés DGAC, associations UAS)
- Contenu : avant/après du rapport, démo vidéo sur terrain (clé pour la crédibilité)
- Bouche-à-oreille : pilotes se recommandent entre eux dans les formations UAS
- CI/CD : déploiement automatique sur Vercel via GitHub Actions

## Dependencies

- Validation du format PDF auprès de 3-5 commanditaires (à faire en parallèle de la construction)
- Stripe KYC/onboarding (prévoir 1-2 jours)
- Domaine + identité de marque DroneReport
- **RGPD (obligatoire avant lancement en France) :** rédiger politique de confidentialité +
  mentions légales (données personnelles dans les photos, emails, données de mission).
  Durée de rétention des photos (48h) à documenter. Prévoir un DPD si collectivités ciblées
  en phase 2. Budget : avocat spécialisé ou LegalStart (~500€) ou modèle CNIL adapté.

## The Assignment

**Avant d'écrire une seule ligne de code :** contacter 3 donneurs d'ordre (mairies,
syndics, artisans couvreurs...) qui commandent des inspections drone aujourd'hui et leur
poser une seule question : "Quand vous recevez un rapport d'inspection drone, qu'est-ce qui
vous manque ou vous agace le plus ?" Leurs réponses définissent la structure du PDF V1 —
et peuvent révéler un problème plus douloureux côté commanditaire que côté pilote.

#### CLAUDE SUBAGENT (design — independent review)

**Critical gaps (auto-approved for inclusion):**

**[D-CRIT-1] Zone pre-population from inspection type** — Step 3 forces manual zone entry. A pilot selecting "toiture" in step 2 should get default zones (Pan Nord, Pan Sud, Rive Est, Rive Ouest) pre-populated, editable but not required from scratch. Auto-approved (P1 completeness, ~1h dev effort).
→ Plan fix: Add "Templates de zones par type d'inspection (toiture, façade, infrastructure)"

**[D-CRIT-2] Camera capture not specified** — Step 5 photo upload must include `accept="image/*" capture="environment"` on the file input. Without this, mobile users get a file picker instead of the camera directly. Auto-approved (P1 completeness, 1 attribute).
→ Plan fix: Specify `<input type="file" accept="image/*" capture="environment">` for mobile photo capture.

**[D-CRIT-3] AI suggestion loading state** — Step 4 "Suggérer" button has no specified loading state. User sees nothing for up to 3 seconds. Auto-approved (P1 completeness).
→ Plan fix: Add loading state: bouton "Analyse en cours..." + spinner → suggestions affichées ou disparaissent silencieusement en cas d'échec.

**[D-CRIT-4] Error states unspecified (3 critical paths):**
- Upload failure: "Photo trop lourde (max 5 MB) / format non supporté / erreur réseau — Réessayer"
- Payment failure: "Paiement refusé — vérifiez votre carte ou réessayez. Vos données sont sauvegardées."
- PDF generation failure: "Erreur lors de la génération — vos données sont sauvegardées. Réessayer."
All auto-approved (P1 completeness).

**[D-CRIT-5] Offline/reconnect behavior** — localStorage restores form data, but no spec for what user sees when they return to the app after connectivity loss. Auto-approved (P1 completeness).
→ Plan fix: Sur rechargement de page, si draft localStorage présent, afficher banner "Rapport en cours — Continuer" avec bouton pour reprendre au bon step.

**[D-CRIT-6] No Edit deep-link from PDF preview** — Step 6 preview has no "Modifier" link back to originating steps. Auto-approved (P1 completeness).
→ Plan fix: Chaque section du PDF aperçu a un lien "Modifier" qui renvoie au step correspondant (step 2, 3, 4, 5).

**High gaps (auto-approved):**

**[D-HIGH-1] No value hook on landing** — Step 1 email field has no context. Add: "Rapport d'inspection professionnel en 10 min — 9€" + miniature PDF sample above the email field. Auto-approved (P1, minimal dev).

**[D-HIGH-2] Empty state zones list** — Before user adds zones, list must show: "Aucune zone — appuyez sur + pour commencer". Auto-approved (P1).

**[D-HIGH-3] Per-photo upload progress** — Each photo shows `pending / uploading (X%) / done / failed` status. "Générer l'aperçu" button disabled until all photos are done. Auto-approved (P1+P2).

**[D-HIGH-4] PDF page render progress** — On mobile with 10 photos, react-pdf may take 5–15s. Add per-page render progress indicator. Auto-approved (P1).

**[D-HIGH-5] UI copy specificity** — All button labels, placeholder text, and empty state copy must be specified before first component is built. Key items:
  - Step 1 CTA: "Créer mon rapport"
  - Step 2 météo: dropdown (Ensoleillé / Nuageux / Pluvieux / Vent fort)
  - Step 4 sévérité labels: "Faible / Modéré / Grave / Critique"
  - Step 4 AI button: "Obtenir une suggestion IA"
  - Step 7: prix affiché "9,00 €" avant redirection Stripe
Auto-approved (P1, zero dev effort).

**[D-HIGH-6] Touch targets** — 44px minimum on all interactive elements. Particularly: zone add/delete buttons, anomaly severity selector (chip buttons, not dropdown), photo delete. Auto-approved (P1).

**[D-HIGH-7] Session recovery** — "Continuer votre rapport" prompt on landing page if localStorage draft exists. Auto-approved (P1).

#### CLAUDE SUBAGENT (eng — independent review)

**Critical issues (auto-approved for inclusion):**

**[E-CRIT-1] Claude Haiku API key must NOT be client-side** (confidence 10/10)
The Anthropic API key cannot be bundled in the frontend JS — it is trivially extractable via DevTools. Must go through a Supabase Edge Function.
→ Plan fix: All calls to Claude Haiku proxied via `/api/haiku-suggest` Edge Function. Rate-limit: 10 suggestion calls per session. API key in Supabase env vars only. Auto-approved (P5, obvious architecture fix).

**[E-CRIT-2] Stripe payment unlock must be synchronous, not webhook-primary** (confidence 10/10)
Webhook delivery can fail. If the primary unlock gate is `checkout.session.completed` webhook, users who pay may not receive their PDF. Fix: On Stripe success redirect, call `/verify-payment?session_id=X` which does a synchronous Stripe API lookup, unlocks report immediately, and queues email separately. Webhooks become secondary confirmation only.
→ Plan fix: "Stripe success redirect → /verify-payment (synchronous Stripe API check) → unlock report → start email send async". Webhooks as idempotent secondary confirmation. Auto-approved (P1, critical path fix).

**[E-CRIT-3] react-pdf OOM on Android with 10×5MB photos** (confidence 9/10)
50MB raw JPEG loaded into browser memory + react-pdf canvas renderer = OOM on low-end Android (2-3GB RAM, constrained WebView heap).
→ Plan fix: Resize photos on `<input>` change using `createImageBitmap` + OffscreenCanvas. Cap embedded resolution at 1200px wide, max 200KB per embedded image before PDF injection. Enforce this before "Générer l'aperçu" is enabled. Auto-approved (P1, directly solves crash path).

**[E-CRIT-4] Dual identity model — schema must be unified before first line of auth code** (confidence 9/10)
Pay-per-report users and subscribers share overlapping identity. The upgrade path (pay-per-report → create account) must preserve: report record, photo URLs, billing history. If pay-per-report creates a `session_id`-keyed record rather than a `user_id`-keyed record, upgrade is lossy.
→ Plan fix: Pay-per-report users are created as Supabase anonymous auth sessions (or email-OTP minimal auth). All records reference `user_id` from day 1. Upgrade = merge anonymous auth into named auth, foreign keys already correct. Document schema decision before any Supabase table is created. Auto-approved (P1+P5, blocking architecture decision).

**[E-CRIT-5] 48h photo cleanup can delete active session photos** (confidence 9/10)
The retention clock must start at payment confirmation, not upload. Add `locked_until` timestamp on storage objects set to `payment_confirmed_at + 48h`. Cleanup job must respect this field.
→ Plan fix: Supabase Storage cleanup function: `DELETE WHERE created_at < NOW() - INTERVAL '48h' AND locked_until IS NULL OR locked_until < NOW()`. Auto-approved (P1).

**High issues (auto-approved):**

**[E-HIGH-1] Supabase Storage upload — no per-file atomicity** (confidence 8/10)
If photo 7 of 10 fails, no recovery path defined. User doesn't know which ones failed. Retrying re-uploads all.
→ Plan fix: Per-photo upload state machine: `pending | uploading | done | failed`. Store upload state in component state + localStorage. "Générer l'aperçu" disabled until all `done`. Individual retry button per failed photo. Auto-approved (P1+P2).

**[E-HIGH-2] Stripe webhook idempotency** (confidence 9/10)
Stripe retries webhooks; Supabase Edge Functions can cold-start and timeout, triggering duplicates. The webhook handler must be idempotent: store `stripe_checkout_session_id` with unique constraint; first action is an upsert that is a no-op if already processed.
→ Plan fix: Add to Edge Function spec: "Idempotent on stripe_checkout_session_id — upsert with unique constraint". Auto-approved (P1).

**[E-HIGH-3] Payment bypass via predictable download URL** (confidence 9/10)
PDF download URL must include a cryptographically random token (UUID v4), generated at report creation, only returned to user after payment verification. Storage path must not be guessable.
→ Plan fix: `reports.download_token = uuid4()` — generated at creation, stored server-side, returned only from /verify-payment. Auto-approved (P1+security).

**[E-HIGH-4] react-pdf French accented characters** (confidence 9/10)
react-pdf uses PDFKit, not the browser renderer. System fonts don't exist in PDFKit. French accented characters (é, è, ê, ç) render as boxes without an explicitly registered Unicode font.
→ Plan fix: Register Noto Sans (full Latin-1) in react-pdf setup. Test with accented text on day 1 of PDF implementation. Auto-approved (P1, zero-surprise fix).

**[E-HIGH-5] RGPD is a launch-blocking pre-requisite, not a documentation task** (confidence 9/10)
Photos containing property addresses and owner identities are personal data under RGPD Art. 4. Minimum before French launch: sign Supabase DPA, define lawful basis, publish privacy notice. Current plan treats RGPD as a "dependency" without specific legal actions.
→ Plan fix: RGPD upgraded from "dependency" to "launch gate": Supabase DPA signed + privacy notice published + lawful basis defined (legitimate interest for B2B inspections, or consent for natural persons). Budget ~500€ (LegalStart or CNIL model). Auto-approved (P1, obligatoire).

**[E-HIGH-6] localStorage cross-tab corruption** (confidence 8/10)
Two browser tabs = two auto-save writers to same localStorage key = last write wins. Silent data loss.
→ Plan fix: localStorage key = `dronereport:draft:{session_uuid}`. session_uuid generated on "Créer mon rapport" click. On app load, scan for existing draft keys; if found, offer "Continuer votre rapport" prompt. Auto-approved (P1+P2).

**Medium issues:**

**[E-MED-1] Magic-link delivery failure** — Gouvernement/collectivité email providers often block magic-link emails. Add fallback: 6-digit OTP code as alternative. Surfaced but medium priority for V1 (primarily targets auto-entrepreneurs, not fonctionnaires yet). Auto-approved defer to V1.1.

**Taste Decision (surfaced at Final Gate):**

**[TASTE-2] react-pdf client-only vs server-side fallback** — The engineering subagent recommends adding a server-side PDF generation fallback (Puppeteer or react-pdf on Node via Edge Function) to handle client-side OOM failures. This adds significant complexity for V1 but eliminates the "paid and received nothing" failure mode. Alternative: enforce strict photo downscaling (E-CRIT-3 fix) to prevent OOM instead.
→ Surfaced at Phase 4 gate. User decides between: (A) client-only + aggressive photo compression, or (B) server-side fallback for robustness.

## Design System Visuel

Généré par /design-consultation le 2026-05-26 — **APPROUVÉ 2026-05-26**
Direction mémorable : "Le PDF inspire confiance de cabinet. L'app se remplit à toute vitesse, un doigt, tête baissée sur le toit."

### Aesthetic Direction

**Instrument de précision**
Ni froid high-tech, ni startup-cute. Comme un bon outil de mesure français : fiable, sobre, expert.
Le commanditaire ouvre le PDF et dit "a été fait par un professionnel".
Le pilote déroule le formulaire sans réfléchir.

- Decoration level: minimal — la typographie fait le travail
- Layout: grid-disciplined, mobile-first
- Reference: cadastre, rapport de cabinet notarial, instruments de mesure industriels

- **Unité de base :** 8px
- **Densité :** comfortable (mobile-first, 44px minimum sur tous les éléments interactifs)
- **Échelle :** 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64

### Layout

- **Approche :** grid-disciplined, une colonne
- **Max width mobile :** 480px (plein écran sur téléphone)
- **Max width desktop :** 640px (formulaire centré)
- **Border-radius :**
  - `--r-sm: 6px` — chips de sévérité, badges
  - `--r-md: 10px` — champs, boutons, cards
  - `--r-lg: 14px` — zone-cards, modales
- **Progress indicator :** 6 segments linéaires dans le topbar (navy fond, blanc actif, ambre complété)

### Motion

- **Approche :** minimal-fonctionnel — seulement ce qui aide à comprendre
- **Transitions d'étapes :** 200ms ease-out (slide horizontal ou fade)
- **Spinners :** bouton "Analyse en cours..." + cercle rotatif pendant appel Haiku
- **États de chargement :** barre de progression par photo (linéaire, navy fill)

### Choix sûrs (la catégorie les attend)

- Layout une colonne sur mobile — pilote, un pouce, toit
- Marine foncé pour l'action primaire — courant dans le B2B français
- Progress indicator linéaire 6 étapes — attendu sur formulaires multi-étapes

3. **Instrument Sans + Geist Mono** — aucun concurrent dans ce créneau ne les utilise.
   Double sens sur "Instrument" = outil de mesure = drone inspection. Identité mémorable.
